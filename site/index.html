Find out a service is down before your users write to you.

Monita checks the URLs and cron jobs of every project your team runs. When one fails, it opens an incident, alerts the people you choose, and shows the outage on a public status page.

Small enough to run on a server you already have

  • One program and one file. Monita is a single binary of about 31 MB, a 13 MB download, that keeps all its data in one SQLite file. It does not need Docker, a separate database or a message queue.
  • Light on memory. In a two-minute test on a Mac, Monita used about 21 MB of memory while it checked 100 URLs every 30 seconds.
  • Easy to connect. A project needs a health URL, one curl line per cron job and, for bug reports, two HTTP calls. See each one below.
  • Alerts survive a restart. Monita saves every alert before it sends it, and it tries again after a failed delivery or a restart. A slow mail server never delays a check.

Install on Linux

These commands download version 0.1.0 from the releases page and install it on an x86-64 server.

curl -fsSLO https://github.com/PT-Perkasa-Pilar-Utama/monita/releases/download/v0.1.0/monita_v0.1.0_linux_amd64.tar.gz
tar -xzf monita_v0.1.0_linux_amd64.tar.gz
sudo install -m 0755 monita /usr/local/bin/monita
sudo monita setup
sudo monita service install

monita setup asks for the public URL, the mail server and the first admin account. monita service install starts Monita now and after every reboot.

You can also try the demo in your browser first. It needs no account.

How a project connects to Monita

Your project does not need a library or an agent. Monita calls your health URL, and your jobs and your backend call Monita over plain HTTP.

Add a monitor with your health URL in the dashboard. Every 30, 60, 180 or 300 seconds, Monita makes this request. An answer with a 2xx status within 10 seconds passes. You can also require a word in the body.

curl -fsS -m 10 https://shop.example.com/healthz

Add a heartbeat and copy its URL. The job calls the URL when it finishes. If the call does not arrive in time, Monita opens an incident. A call to /fail opens one at once, and the first kilobyte of its body becomes the cause.

0 2 * * * /opt/jobs/backup.sh && curl -fsS -m 10 https://monita.example.com/ping/<token>

Pings arriving on time

Paste a Slack or Microsoft Teams incoming-webhook URL into the project's alert settings. Monita posts JSON like this when an incident opens and when it closes. It also emails the addresses you list.

{
  "text": "[CRITICAL] Payments / API health is down: HTTP 503, expected 2xx after 2 checks",
  "event": "incident.opened",
  "project": "payments",
  "severity": "critical",
  "incident_url": "https://monita.example.com/projects/payments/incidents/42"
}

Link to the project's public status page, or build your own banner from its JSON. The endpoint is public and allows requests from any origin.

curl -s https://monita.example.com/api/v1/public/status/payments?days=30
{ "data": { "overall": "down", "items": [ { "name": "API health", "state": "down", "uptime_90d": 99.95 } ] } }

Your backend asks Monita for a reference ID with the project's API key and gives it to the user. The user then sends a ticket with it, from your app or from the status page. Monita stores only a hash of the ID, so it never learns who the user is.

curl -s -X POST https://monita.example.com/api/v1/ref-ids \
  -H "Authorization: Bearer $MONITA_KEY" -H 'content-type: application/json' \
  -d '{"single_use": false}'

curl -s -X POST https://monita.example.com/api/v1/tickets -H 'content-type: application/json' \
  -d '{"ref_id": "rf_...", "title": "Checkout button does nothing", "description": "I click Pay and nothing happens."}'

What Monita does when a check fails

This is the sequence for an HTTP monitor that checks every 30 seconds. A single failed check does not alert anyone, because one dropped request is common. The second failure in a row opens the incident.

api.example.com/healthz
    1. The first check failsHTTP 503. Monita waits for the next check.
    2. The second check failsTwo in a row open an automatic incident.
    3. Your team hears about itAn email to the addresses you list and a webhook to Slack or Teams, through an outbox that retries.
    4. Users see itThe status page shows the incident and every update the team posts.
    5. The first passing check closes itMonita sends a recovery alert with the downtime.

    What Monita does not do

    Read these before you install it. Each one is a choice for version 1, and some of them can change.

    • It checks from one place. Every check runs from the server that runs Monita, so Monita cannot tell a regional outage from a local one.
    • It checks HTTP only. TCP, ping and DNS checks are not in version 1.
    • It alerts by email and webhook. It does not send text messages, make phone calls or manage an on-call rotation.
    • It signs people in with an email and a password. Single sign-on and two-factor sign-in are not in version 1.
    • It keeps single checks for 7 days. Daily summaries stay for good, so the uptime history stays complete.
    • Tickets hold text only. Users cannot attach files to a bug report.
