# Monita v1.1 scope: decisions

Date: 2026-10-19

A comparison with Uptime Kuma and Gatus named five things Monita lacks: more check types, more alert channels, maintenance windows, two-factor sign-in, and checks from more than one place. The v1 scope log deferred the first, the second and the fourth to the user ([Deferred](2026-10-16-monita-v1-scope.md#deferred)). The user asked for all five in the next version. This log decides what 1.1 builds, what waits, and why.

The motto still holds: one binary, one file, small footprint. A gap that needs a raw-socket privilege, a new TLS stack or a second kind of process waits.

| # | Question | Decision | Why |
|---|----------|----------|-----|
| Q16 | Which new check types? | A monitor has a kind: `http` (as today), `tcp` or `dns`. A TCP check passes when a connection to `host:port` opens within the timeout. A DNS check resolves a host name with the server's resolver; it passes when the name resolves, and, if the tech lead sets an expected address, when one A or AAAA answer equals it. The intervals, the timeout, the failure count, severity, the switches and the status page work as for HTTP. Method, headers, body, sign-in, expected status and keyword apply to HTTP only. Migration 0024. | `tokio` opens TCP connections and resolves names with no new dependency. These two cover databases, mail and queue ports, and DNS outages. |
| Q17 | Which alert channels? | Each severity's webhook gets a format: `json` (today's body, for Slack, Google Chat and any receiver), `discord`, `telegram`, `ntfy` or `pagerduty`. Telegram needs a chat ID and PagerDuty a routing key, kept in one more field that, like the URL, a supervisor never sees. PagerDuty triggers on open and resolves on close, keyed by the incident. Email stays as it is. The ticket webhook keeps the `json` format. Migration 0025. | Each is one HTTP POST through the outbox that already retries, with a different body. No new dependency. |
| Q18 | How do maintenance windows work? | A tech lead plans a window on a project: a title, a start, an end, the monitors and heartbeats it covers, and an optional public message. While a window is active, checks still run and record results, but a failure opens no incident and sends no alert. An incident already open stays open and closes as usual. When the window ends, a check that still fails opens an incident at once, because its failure count kept counting. The status page shows covered items as Maintenance and the message as a banner. Availability does not count maintenance as downtime. One-off windows only. Migration 0026. | Planned work then neither pages the team nor shows as an outage, and real trouble after the window is not missed. |
| Q19 | How does two-factor sign-in work? | Each user may turn on a TOTP code (RFC 6238: SHA-1, 6 digits, 30 seconds, one step of drift either way, no code used twice). Turning it on shows the secret and an `otpauth://` link, and asks for one code to confirm. It also shows 10 recovery codes once; only their hashes are stored. Sign-in asks for the code after the password. A super admin can turn a user's two-factor off, and `monita admin reset-password` turns it off for a super admin. The secret is stored as entered, like project secrets (SEC-23), because Monita must compute the code. Migration 0027. | HMAC over `sha1_smol`, which `uuid` already builds, is a few lines, so no new crate is compiled. No QR code: the secret and the link work in every authenticator app. |
| Q20 | Checks from more than one place? | Superseded by Q26 on 2026-10-21. Was: not in 1.1, a v2 design: `monita probe --server <url> --token <key>` runs checks elsewhere and reports to the server; the server assigns monitors to locations; a monitor is down only when N of M locations agree; locations get their own table and tokens. It needs its own decision and a technical-spec chapter before code. | It adds a second kind of process, agent sign-in and a voting rule. That is architecture, not a feature. |
| Q24 | ICMP ping checks? | Yes, in 1.1 (2026-10-21, the user's call, #7). A monitor kind `ping` takes a host name or an address. One echo request per check through an unprivileged ICMP datagram socket (`socket2`, already compiled in); a reply within the timeout passes, and the latency is the round trip. Linux allows the socket when `net.ipv4.ping_group_range` covers Monita's group; systemd 243 and later and Docker set `0 2147483647` by default. When the system refuses it, the check fails and the error names that setting. Windows has no unprivileged ICMP socket, so the form refuses `ping` there. Migration 0029 rebuilds `monitors` to widen the `kind` CHECK. | No raw socket, no capability in the service unit, no new crate. TCP still covers a host that blocks ICMP. |
| Q25 | Warn before a TLS certificate expires? | Yes, in 1.1 (2026-10-21, the user's call, #8). An HTTP monitor of an `https://` URL may warn 7, 14 or 30 days before its certificate expires. Each check reads the leaf certificate's `notAfter` through reqwest's `tls_info` and keeps it on the monitor. When the expiry is inside the window, Monita sends one `certificate.expiring` alert through the warning route, once per certificate: a renewal brings a new `notAfter`, which warns again in its own time. No incident opens. The monitor's alert switch off sends nothing. PagerDuty gets a trigger keyed `cert:{monitor}:{notAfter}` and no resolve. Migration 0028. | reqwest already hands over the peer certificate, so a short DER reader is the whole cost. An expired certificate on a strict check fails the check anyway; the warning comes first. |
| Q26 | Checks from more than one place? | Yes, in 1.1 (2026-10-21, the user's call, #6). Design in [technical-specs 14](../technical-specs/14-locations.md), written before the code. A super admin adds a location and gets its token once. `monita probe` runs on another machine, pulls due checks for its location, runs them with the same probe code and posts the results. A monitor checks from this server and from any locations the tech lead picks. It counts a check as failed when at least `min(quorum, fresh)` of the locations with a fresh result failed, and that verdict feeds the incident engine. Migration 0030. | The second process is the same binary, so nothing new ships. The verdict rule is pure and tested on its own. |
| Q27 | Does a new project's critical route call its webhook? | No (2026-10-21, the user's call). Both severities start with the webhook unticked; the owner ticks it and sets a URL. Migration 0033 unticks routes that had no URL, which could never send anything. Routes with a saved URL keep their choice. AC-15.02 changes with it. | A ticked box over an empty required URL blocked saving the email list, and a default nobody can use is noise. |
| Q28 | Does a new project's status page show the Changelog tab? | Yes (2026-10-21, the user's call). A new project starts with it on, and its empty state reads "No release is published yet." Existing projects keep their setting: turning the tab on for them could publish releases a team wrote while it was hidden. | A team that writes releases should not have to find a switch first. |
| Q29 | How does Monita nudge a user to turn on two-factor sign-in? | A one-row note under the top bar while it is off (2026-10-21, the user's call). Its X closes it for that user in that browser only (`localStorage`), so a new browser shows it again. Two-factor stays optional (Q19). The avatar menu's item became **User settings**, a side-nav area like Admin. | A nudge each new browser, without forcing anyone or storing a dismissal on the server. |
| Q30 | What does changing your own password do? | It needs the current password and ends every other session of the user; the session that changed it stays (2026-10-21). An account gets 10 tries per fixed 15-minute window, counted right or wrong before the check, so a stolen session cannot guess the password. | Matches a new invite, which also ends the old password's sessions at once. |
| Q31 | Can a user set a picture? | Yes, in **User settings**, **Profile** (2026-10-21, the user's call). It is stored and checked as a project icon is (PNG or WebP, at most 32 KB, scaled in the browser; `user_avatars`, migration 0034). Only its owner reads it, at `/me/avatar`; the top bar shows it. | Pages show only your own picture now. A route for other users' pictures waits until a page needs one. |
| Q32 | How long does a key shown at two-factor setup wait for its first code? | 10 minutes (2026-10-21, the user's call). After that the confirm step refuses it, and retention clears it. Two-factor stays off the whole time, and a new **Turn on** replaces the key anyway. Migration 0035 adds `totp_pending_expires_at` and drops keys that waited before it. | A key left on a screen should not stay usable for ever. |
| Q33 | Can every project use one Telegram bot? | Yes (2026-10-21, the user's call). A super admin sets the global Telegram bot in **Admin**, **Telegram**. A severity's new format `telegram_bot` posts through it. The user asked for a username only, but the Bot API sends to a person or a private group by numeric chat ID alone (`@name` works for public channels). So a project connects a chat with a link: `t.me/<bot>?start=<code>`, or `startgroup` for a group; the page reads the bot's messages with `getUpdates` and fills the chat ID. The token lives only in `settings`; outbox rows name the chat, and delivery adds the token. Migration 0036 adds `telegram_links` and rebuilds `alert_routes` and `outbox` for the new format and channel. `MONITA_TELEGRAM_API` points at a self-hosted Bot API server. | One bot to set up for the whole department, and no token copied into every project. |
| Q34 | How does a project route its alerts? | Alert cards replace the two severity routes (2026-10-21, the user's call). Every project has two fixed **Owner email** cards, one for critical and one for warning, which email the current owner and change only by their switch. A project adds up to 10 of its own: an email list or a webhook in one format. A card listens to critical, warning or both, and has its own switch and test. An alert goes to every card that is on and listens; an address in several cards gets one email. With no card listening an alert goes nowhere, the incident still opens, and the page says which level no one hears. Migration 0037 converts the routes so nobody who got alerts stops getting them, and drops `alert_routes`. Telegram connect links now belong to the project, not a severity. | Two fixed routes allowed one webhook per level; teams want several channels, and one channel for both levels. |
| Q35 | How long must a password be? | 8 characters or more, down from 12 (2026-10-21, the user's call). It applies to invites, `monita admin create`, `monita setup` and the Password page. Existing passwords keep working. | Shorter passwords are easier for the team to adopt. Sign-in stays rate-limited and two-factor is available. |
| Q36 | Do ticket alerts get formats, and how do forms offer the global Telegram bot? | Ticket alerts stay their own section, apart from cards, and their webhook picks a format: JSON, Discord, Telegram, the global Telegram bot or ntfy (2026-10-21, the user's call). Not PagerDuty: a ticket is no incident, so its trigger would never resolve. Migration 0038. In every form, the global bot is not a format in the list: a Global Telegram or Custom switch comes first, shown once a bot is set up. Pages call it the global Telegram bot, never Monita's bot, because each adopter sets up a bot of their own. | Monita is open source. The bot belongs to whoever runs it. |
| Q37 | How does a project set up ticket alerts? | Ticket alerts are alert cards in their own section (2026-10-21, the user's call; this replaces the "own section" part of Q36). Each project has three fixed owner cards: daily digest, new tickets, ticket moves. A new project has all three off; AC-30.01 no longer turns the digest on by default. A project adds up to 10 ticket cards of its own, apart from its 10 incident cards. A ticket card is an email list or a webhook in JSON, Discord, Telegram, the global Telegram bot or ntfy. It listens to new tickets, moves or both. Never PagerDuty, and the digest only on the owner's card. A card hears incidents or tickets, never both. Migration 0039 keeps the digest's state and turns a saved ticket webhook into a card. Alert cards ask for no name: a card takes its kind, or its Telegram chat. | One way to set up every alert. The old section mixed a switch, three boxes and a webhook in one form. |
| Q38 | How does a tech lead stop a monitor or heartbeat for a while without deleting it? | Pause, apart from maintenance (2026-10-22, the user's call). While paused nothing checks it, no deadline is watched, nothing opens and no alert goes out. A heartbeat still stores its pings. Pausing closes an open automatic incident without an alert ("Paused by a tech lead.") and resets the streak. A resumed monitor checks at once; a resumed heartbeat's deadline starts from now. A paused system leaves the public status page. Migration 0040. | Deleting loses history and the ping URL. A maintenance window still checks and is meant to end. |
| Q39 | What does the Overview show first? | One chart of the last 24 hours instead of three tiles (2026-10-22 and 2026-10-26, the user's call). Monitors draw as response-time lines on a log scale: the 5 that need the team (down, issue, maintenance, no data yet, up; then the most failed checks; then the slowest) in colour, every other one faint. Heartbeats have no latency, so they draw as lanes of ping marks on the same time axis: 6 lanes, ranked by state, failures, time down and nearness to the deadline, and one lane for the rest. 15-minute slots, a hover readout, and every line and lane opens its page. It reads again every 30 seconds. The project list opens on the same chart with a project as each series (2026-10-26): the mean response time of its monitors, red where a monitor was down, and a lane of its heartbeats' pings, so monitors and heartbeats read apart; the list under it. The view picked last is remembered. | It must stay readable with 50 monitors and 50 heartbeats. A min-to-max band across HTTP, TCP and DNS covered the whole plot, so the rest draw as faint lines. |
| Q40 | How does a ping check run where the ICMP socket is refused, and on Windows? | It runs the system `ping` once (2026-10-22, the user's call). A reply is a line with `TTL=`, not the exit code. The time reads from `time=` or `time<` in any language. Docker opens the socket by default, so the image needs no `ping`. | No new dependency and no privilege for Monita. |
| Q41 | How does a user who lost the authenticator and the recovery codes get back in? | `monita admin reset-sign-in --email`, on the server (2026-10-22, the user's call). It works for any active user, turns two-factor off, stops the old password, and emails a link to set a new one. It prints the link for when mail does not work. | Whoever runs the server can already read the database, so the CLI is the fail-safe. |
| Q42 | Does Monita send mail to its own sender address? | No, unless an active user signs in with that address (2026-10-22, the user's call). Delivery drops the row unsent. | Such mail loops back into the mailbox that sent it. |
| Q45 | Does Monita limit callers per IP address? | No (2026-10-26, the user's call). An office, a school or a mobile carrier puts many people behind one address, and one mistake there locks them all out. Sign-in takes 10 wrong passwords per account per 15 minutes instead. Wrong API keys, ping tokens and invite links are not limited, because each is random. Migration 0043 drops `rl_ip_per_min`. | Guessing a password is the one attack a limit must stop, and a per-account budget stops it without touching anyone else. Someone who knows an email can hold that one account for 15 minutes. |
| Q44 | Can a project API key do more than issue ref IDs? | Yes (2026-10-26, the user's call: keys looked like a project management API but only issued ref IDs). A key has a scope: `ref_ids`, `read` or `write`. A `read` or `write` key reaches its own project's detail, monitors, heartbeats, incidents and maintenance under `/api/v1/projects/{slug}/`, through the team's own handlers. A `read` key sees what a supervisor sees. A key's update names the key, never a user. Keys, secrets, alert cards, tickets and project delete stay off it. Old keys stay `ref_ids`. Within v1 a field may be added, never removed or renamed. | Scripts and pipelines can pause a monitor for a deploy or post an update without a person's session, and a leaked key reaches one project and none of its secrets' values. |
| Q43 | How does the project list filter by state? | By the badge each card shows (2026-10-26, the user's call): Down when a monitor or heartbeat has an open automatic incident or is down with its incident switch off; Issue when one is in an open manual incident and none is down; Up for the rest, including maintenance, waiting and paused. On the server, so paging and the count follow it. | A filter that disagreed with the badges would confuse more than no filter. |
| Q46 | Can a team take an outage that was not one out of its uptime? | Yes, two ways (2026-10-26). A tech lead reclassifies an incident as planned work (maintenance, or a pause that came too late) or as a false alarm (the check was wrong), and can count it again later: `PUT .../incidents/{id}/class` and migration 0044. A reclassified incident closes if it is open, and leaves availability, the charts and the public status page. The team still sees it, tagged, with who changed it. Past days change at once, because every figure works out downtime from the incidents. And a failed check or ping inside an active maintenance window is stored with `in_window = 1` (migration 0045) and counts as good on the charts and in the daily summary, which draw the window as stripes. | A pause or a window is often set a minute too late, and a flaky check is not downtime. Without a way out, uptime would punish the team for planned work, and the public number would be wrong. Deleting the incident would erase what the team saw, so the class keeps it. |
| Q47 | Which engine reads and writes the database file? | SQLite itself, through `rusqlite` with SQLite compiled in, instead of Turso 0.8.3 (2026-10-26, the user's call). The file format does not change: a database Turso wrote opens as it is, and migration 0047 drops Turso's three unused counter tables. One writer under a lock and pooled readers, WAL, full sync on commit, a 5 s busy timeout, and a lock file beside the database so a second Monita process stops at open, as under Turso. Proof before the switch: the parity kit in `scripts/parity/` found 0 differences on 852 requests and 28,853 table rows, all 428 Rust tests and the same 56 browser tests pass, and no read or write got slower on 3 million checks. | Monita used none of what Turso adds: the async API ran on blocking reads, and its concurrent writes and encryption are experimental by Turso's own manual. Turso cost a pre-1.0 engine with known quirks, unused code in the binary, and a build that ran out of memory in a 3 GB VM. SQLite is the most tested database engine there is. |
| Q48 | How does a user keep the projects, monitors and heartbeats they care about in front? | Pins (2026-10-27, the user's call: easy to find, low friction). Each user pins up to 6 projects, and up to 6 monitors and 6 heartbeats in each project. A pinned row goes first in its list, in the list's own order among the pins; the project list orders pins first on the server, so they land on page 1. Pinned monitors are always drawn as lines on the Overview chart, first, and the line count grows to fit 6; pinned heartbeats take the first lanes; pinned projects lead the projects chart. The pin button sits on every row and card, faint until pointed at and solid once pinned; a click flips it at once with an Undo, and at the cap the message names the one to unpin. A supervisor pins too (a personal setting, `AccountUser`); an API key never does, and its answers say `pinned: false`. Three tables cascade with their user or target (migration 0048). | The charts already pick what needs the team; a pin lets each person add what they watch every day, without a setting page or a dialog. |
| Q49 | How does a super admin start a location's probe, and how often does an idle probe call? | A setup panel and long polling (2026-10-26). Add location and New token open a panel with three ready commands, this Monita's address and the token already in them: Docker, a Linux service (`monita probe install`, a systemd unit with its token in a root-only env file) and a run in a terminal. The panel turns to Connected when the probe first calls; the token shows only there. New token stops the old token at once. The probe asks for work with `wait=25`: the server holds the request until a check falls due, for 25 seconds at most, and naps 1 to 5 seconds between looks. | A location that a super admin cannot start in one paste is a location nobody uses. Polling each second cost 3.04 s of CPU a minute for 8 idle probes on the demo server; long polling cost 0.55 s, and a monitor given a location is still seen within 5 seconds. |
| Q50 | Can a maintenance window change after it is planned? | Yes, until it ends (2026-10-27). A scheduled window changes every field. An active window changes its title, message and end, so work that runs long gets more time. Its start and items stay. An ended window stays a record. `PUT .../maintenance/{id}` reads the state again inside the write. | Delete and plan again was the only way, and it is impossible for an active window. An active window keeps its items: the checks it already holds carry `in_window`, and the chart of an item taken out would lose the stripes over checks that still count as good. Every held failure looks again within 60 s, so a new end takes effect within a minute. |
| Q51 | May a Global Telegram card name any chat ID? | No (2026-10-27, security audit). The shared bot sits in many teams' chats, so a typed ID let one project post into another's. A card takes only a chat that one of the project's own connect links found (`telegram_chats`, migration 0049). A channel connects when an admin posts the `/start` line in it, read as a `channel_post`. The manual Chat ID input is gone. Chats that existing cards use count as proved. | The link proves the team added the bot there, and no alert that works today stops. |

## Deferred

| Branch | Reason | Who decides |
|--------|--------|-------------|
| DNS record types other than A and AAAA (MX, TXT, CNAME) | The system resolver returns addresses only; other types need `hickory-resolver`. | The user, on request from a tech lead |
| Microsoft Teams as a webhook format | Teams Workflows expect Adaptive Card bodies; untested here. The `json` format reaches Teams through a Workflow that maps `text`. | The user |
| Recurring maintenance windows, required two-factor for every user | Not needed for a first version of either feature. | The user |
