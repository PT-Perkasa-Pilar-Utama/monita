# Monita v1.2 scope: decisions

Date: 2026-11-23

Two issues plan the next minor version: a compact Projects view ([#18](https://github.com/PT-Perkasa-Pilar-Utama/monita/issues/18)) and project reports as PDF ([#17](https://github.com/PT-Perkasa-Pilar-Utama/monita/issues/17)). The user delegated their open questions to the advisor. This log records the answers.

## Compact Projects view (#18)

| # | Question | Decision | Why |
|---|----------|----------|-----|
| Q53 | How many projects does the compact view show, and from which route? | 100 a page (`caps::PROJECTS_GRID_PAGE`), from its own route `GET /api/ui/projects-grid` with the list's query (`q`, `owner`, `sort`, `state`, `page`). Each row is `slug`, `name`, `icon_url`, `kind` and `pinned`. Switching to or from the view starts at page 1, because the page size changes. | Twenty icons fill one row, so the view needs a larger page. The full pulse reads the last day and two counts per project; the view needs only the state, so its own route keeps 100 rows cheap. |
| Q54 | Where does a tile's state come from, and in what order do tiles come? | The state is the same `kind` the cards show (the worse of the monitors' and heartbeats' states). The order is the list's: pinned projects first, then the chosen sort. Down projects are not moved first; the State filter shows them. | One rule for a project's state on every view. A view that reorders by state would disagree with the sort the page names. |
| Q55 | What does a tile show? | The project icon, or its first letter, and a ring in the state colour with a glyph for every state except up. The name is hidden on the tile and shows in a tooltip. The link's accessible name is the name and the state, for example "Payments, down". | Colour alone does not tell issue from maintenance (both yellow) and fails for colour-blind people. The view exists to be the most compact one, so the name stays off the tile. |

## Project reports (#17)

| # | Question | Decision | Why |
|---|----------|----------|-----|
| Q56 | Which reports, for whom? | Two kinds, per project, in English: an incident report for one incident, and a summary report for a period. A download shows times on the viewer's clock, as the team pages do (the app's `x-utc-offset`; without it, the admin offset). A scheduled email has no viewer, so it uses the admin offset. The report names the offset it uses. A report shows only what a supervisor sees on screen, and never a monitor's URL. | A tech lead hands the report to a manager or a client. A supervisor's view is the widest one that hides secrets (Q23, SEC-22). |
| Q57 | Where do the numbers come from? | Availability, downtime, the count of outages, the longest incident and the mean time to resolve come from automatic incidents (an outage is an automatic incident not reclassified), as on the status page and the monitor page (`incidents::store::period_stats`). Reclassified incidents (Q46) and manual incidents are not downtime, and maintenance opens no incident (Q18). The mean time to resolve and each system's MTTR are one rule: the mean length of an outage that touched the range, an open one counted to the range's end (from `period_stats`); the project figure weighs each system's MTTR by its outages. Response time is left out, because `daily_summaries` keep UTC days only. | Incident rows are kept while the project exists, so any range works, and the report agrees with every screen. |
| Q58 | How is the PDF made? | A small PDF writer in Monita, with the built-in Helvetica font in WinAnsi encoding: text, lines and filled rectangles, no embedded font. Curly quotes, dashes and the ellipsis print as their ASCII forms, and any other character outside printable ASCII prints as `?`. Text from users is escaped. | No new crate, no font file, no font licence and almost no binary growth (NFR-07). The writer's limit is ASCII text, marked `ponytail:` with its upgrade path: a font-embedding crate that passes `cargo deny`. |
| Q59 | How does a report reach people? | First a download: the incident report from the incident page, the summary report from a project page for the last 7 days, the last calendar month, the last quarter or a range of days up to 366 days. Then a schedule: each project has a weekly and a monthly summary report, each with a switch and up to `caps::EMAILS_PER_CARD` addresses, on its own settings page **Reports**. A weekly report covers Monday to Sunday and a monthly one the calendar month, both in the admin offset, and each goes out at `MONITA_DIGEST_UTC_HOUR` after its period closes, through the outbox with the PDF attached. The period sent last is recorded in the same write that queues the email, so a period is sent once. A supervisor downloads reports and cannot change a schedule. | The user asked for "regular" reports, which is a schedule; the download comes first because the schedule sends the same file. |
| Q60 | How long can a report get? | A report lists at most `caps::REPORT_INCIDENTS` (50) incidents, longest first, and says how many more there are. Every monitor and heartbeat of the project has a row: at most 200 (`caps::SOURCES_PER_PROJECT`). An incident report lists its updates, at most `caps::UPDATES_PER_INCIDENT`. | No unbounded list, on paper too. |
| Q61 | What waits? | An availability target per project, a report across projects, other languages, owners and due dates on action items, and sending a report by itself when an incident closes. The post-mortem, deferred here first, is Q63. | Each adds a setting or a table. |
| Q62 | What does the summary report show? (2026-11-23, after the user asked to follow best practice and drop the counting note) | Four figures (availability, downtime, outages, mean time to resolve); availability by day as one bar a day in the status page's colours; a row a monitor and heartbeat with availability, downtime, outages, MTTR and MTBF; the maintenance time and its share of the period with the windows; and each incident with its alert level and state, when, what it affects, its cause and its latest update. No note on how Monita counts: the guide holds the definitions. No response time, because `daily_summaries` keep UTC days only. No comparison with the previous period. | Site24x7's availability summary report has the top band (availability, outage duration, outage count), MTTR and MTBF per monitor, scheduled maintenance time and percentage, and an availability trend chart ([monitor report](https://www.site24x7.com/help/reports/monitor-reports/monitor-availability-summary-report.html), [group report](https://www.site24x7.com/help/reports/monitor-groups-report/availability-summary-report.html)). Pingdom's uptime report lists each outage with its root cause ([SolarWinds](https://documentation.solarwinds.com/en/success_center/pingdom/content/topics/pingdom-reports.htm)). Neither compares with the previous period. |
| Q63 | Where is the post-mortem? (2026-11-23, the user's call: written by the tech lead and emailed on publish) | A resolved incident can have one post-mortem with Google's sections: summary, impact, root cause, trigger, resolution, detection, action items and lessons learned, each up to 2 000 characters, as plain text. The incident PDF includes it, marked Draft until it is published. Publishing emails that PDF to the addresses under **Settings**, **Reports**, **Post-mortems** (a switch and up to 20 addresses, its own table). Nothing is emailed when an incident closes. `reports` owns both tables (migration 0051); `incidents` and `status` never read them, so a post-mortem never reaches a public page. | Google's example post-mortem has these sections ([sre.google](https://sre.google/sre-book/example-postmortem/)). 8 sections of 2 000 characters at 6 bytes each (a JSON `\u` escape) is 96 000 bytes, under the 128 KiB body cap. |


### Post-mortem states (Q63)

The actor is the project owner or a super admin in every row. A supervisor and an API key get 403. No state is terminal: a published post-mortem goes back to draft to change, and publishing again sends again, marked Updated.

| From | To | Guard | Effect |
| --- | --- | --- | --- |
| none | draft | the incident is resolved | the text is stored |
| none | published | resolved; summary, root cause and resolution are filled | stored, then one email per address |
| draft | draft | none | the text is saved |
| draft | published | summary, root cause and resolution are filled | one email per address |
| draft | none | none | the draft is deleted |
| published | draft | none | the text is kept |

Every other move is refused with 422, as other refused state changes are: publishing a published post-mortem, deleting a published one, or any write while the incident is open.

## Known limits

Found in the review of the first build (2026-11-23). Each names what would clear it.

- A report email that fails all four outbox tries is not sent again, because its period is already recorded as sent. With no mail server set, the email goes to the log and the period counts as sent. The guide says to download the report instead. Clears with a re-queue of the report periods whose emails failed.
- The summary's 50 longest incidents, its Outages figure and its mean time to resolve come from the newest `caps::PROJECT_INCIDENTS` (200) incidents of the range. Past that, the counts read "at least 200" and "or more". Clears with an incidents interface that counts the range and returns its longest rows in SQL.
- A report download has no rate limit of its own. It reads at most 200 sources and 200 incidents, so its cost is bounded. Clears with a per-user bucket in `platform::rate_limit` if downloads ever load the server.
- `platform::pdf` prints printable ASCII only (Q58), and a wrapped message keeps its words but not runs of spaces or tabs, so a pasted log loses its alignment. Clears with the same font-embedding crate and a monospace style for messages.
